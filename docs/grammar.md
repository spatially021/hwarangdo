# 언어 요약

- class는 entity이며 직접 생성할 수 없다.
- entity는 world.spawn으로 생성 → Handle<T>
- Handle<T>는 복사 가능하며 동일한 entity를 가리킨다.
- entity 접근은 world.view(handle) → T (관찰자이며 복사본 아니다.)
- 관찰자는 저장 및 재대입이 불가능하며 메서드 내부에서만 사용할 수 있다.
- entity는 world.destroy(handle)로 제거한다.
- struct는 value이며 일반 값처럼 사용 가능하다.

<!--

## 1.1 목표
<!--
예:
- 게임 개발용 언어
- entity/value 분리
- world 기반 객체 관리
- 안전한 접근 모델
-->

1. 본 언어는 게임 개발을 주요 대상으로 한다.
2. 본 언어는 객체를 entity와 value로 구분하며, 각 범주에 서로 다른 생성, 접근, 수명 규칙을 둔다.
3. entity 객체의 생성과 접근은 handle-view 모델을 따른다.
4. 본 언어는 암시적 동작을 최소화하고, 가능한 한 명시적인 표현을 우선한다.
5. 디버그 환경에서는 엄격한 검증을 우선하며, 릴리즈 환경에서는 불필요한 정지를 최소화하는 방향을 지향한다.
6. 언어 규칙은 게임 객체 관리 모델(world, entity, handle)을 중심으로 설계된다.

## 1.2 비목표
<!--

- 암시적 객체 수명 관리 허용 안 함

1. 본 언어는 범용 시스템 프로그래밍 언어를 목표로 하지 않는다.
2. 사용자에게 임의의 저수준 메모리 조작 수단을 직접 노출하는 것을 목표로 하지 않는다.
3. 편의를 위한 광범위한 암묵적 변환이나 숨겨진 동작을 제공하는 것을 목표로 하지 않는다.
4. 본 언어는 자동 객체 수명 관리를 목표로 하지 않는다.

## 1.3 핵심 개념 요약
<!--

- struct는 value 타입이다.

<!--

## 2.1 타입 분류
<!--
예:
- 기본 타입
- value 타입
- entity 타입
- 참조/관찰 관련 타입
- 특수 타입(void, error 등)
-->
본 언어의 모든 타입은 다음 분류 중 하나에 속한다.
1. value 타입
2. entity 타입
3. 특수 타입

### 2.1.1 기본 타입
<!--
int, float, bool, char, string 등
각 타입 목록을 확정적으로 적기
-->
기본 타입은 본 언어에서 제공하는 기본적인 타입으로 value의 하위 타입이다.
기본 타입은 이하의 분류를 따른다.

| 분류　　　 | 키워드 | 설명　　　　　　　　　　　　　　　　　　　　　　 | 상태　　　| 비고　　　　　　　　　|
| ------------| --------| --------------------------------------------------| -----------| -----------------------|
| 정수　　　 | int　　| 부호 있는 정수 타입군　　　　　　　　　　　　　　| 구현 완료 | unsigned 형 포함　　　|
| 부동소수점 | float　| 부동소수점 타입군　　　　　　　　　　　　　　　　| 구현 완료 | 　　　　　　　　　　　|
| 고정소수점 | fixed　| 고정소수점 타입군　　　　　　　　　　　　　　　　| 구현 예정 | 세부 규칙 미정　　　　|
| 논리　　　 | bool　 | 참/거짓 값을 가지는 타입　　　　　　　　　　　　 | 구현 완료 | 　　　　　　　　　　　|
| 문자　　　 | char　 | 하나의 유효한 Unicode code point를 나타내는 타입 | 구현 완료 | 　　　　　　　　　　　|
| 문자열　　 | string | 문자열 값을 나타내는 타입　　　　　　　　　　　　| 구현 완료 | 내부 표현은 별도 정의 |


### 2.1.2 value 타입
<!--
예: struct
복사/대입/초기화 가능 여부도 요약
-->
value 타입은 일반 값처럼 직접 선언, 대입, 전달할 수 있는 타입이다.
value 타입의 값은 handle-view 모델을 통하지 않고 직접 사용한다.
value 타입에는 기본 타입과 struct 타입이 포함된다.
Handle<T>는 value 타입이다.

value 타입은 다음 성질을 가진다.
- 대입은 값의 복사로 취급한다.
- 초기화는 해당 타입의 초기화 규칙을 따른다.

### 2.1.3 entity 타입
<!--
예: class
직접 생성 불가, world.spawn 필요 등
-->
entity 타입은 handle-view 모델을 통해 다루는 객체 타입이다.
entity 타입은 다음 성질을 가진다.

1. 직접 생성할 수 없다.
2. world.spawn을 통해 해당 entity를 가리키는 handle을 얻는다.
3. entity에 대한 필드 접근과 메서드 호출은 world.view를 통해 얻은 view를 통해 수행한다.
4. world.destroy를 통해 명시적으로 제거할 수 있다.

### 2.1.4 특수 타입
<!--
void, never, error 같은 특수 타입이 있다면 여기 정리
아직 없다면 "미정"으로 적기
-->

특수 타입은 일반적인 value 타입이나 entity 타입과 다른 목적과 규칙을 가지는 타입이다.
현재 확정된 특수 타입은 다음과 같다.
- Option<T>
- Result<T, E>

## 2.2 타입 동일성 규칙
<!--
타입이 같다고 판단하는 기준.
예:
- 이름 기반인지
- 제네릭 인자까지 포함하는지
- Handle<T>와 T는 당연히 다른지
-->
타입의 동일성은 이름 기반으로 판단한다.
단, 제네릭 타입은 타입 생성자와 모든 타입 인자가 동일할 때만 같은 타입으로 본다.

1. value 타입은 타입 이름이 같을 때 같은 타입으로 본다.
2. entity 타입은 타입 이름이 같을 때 같은 타입으로 본다.
3. `Handle<T>`와 `T`는 서로 다른 타입이다.
  ```
  Handle<Player> != Handle<Monster>
  Handle<Player> != Player
  ```
4. 두 제네릭 타입은 타입 생성자와 각 타입 인자가 모두 같을 때만 같은 타입으로 본다.

## 2.3 대입 가능성 규칙
<!--
아주 중요.
"같은 타입이면 대입 가능" 같은 단순 문장으로 끝내지 말고
예외를 반드시 적기.
예:
- value는 대입 가능
- entity 본체는 대입 개념이 없음 / 제한됨
- handle끼리 대입 가능 여부
- 관찰자 대입 가능 여부
-->

대입과 복사 초기화는 다음 규칙을 따른다.

1. value 타입은 동일한 타입 간의 대입이 허용되며, 대입은 값의 복사로 수행된다.

2. 기본 타입에 한하여 일부 암묵적 형변환을 허용한다.
   - 구체적인 형변환 규칙은 별도 섹션에서 정의한다.

3. entity 타입의 관찰자는 복사 초기화와 대입을 허용하지 않는다.
   - 하나의 관찰자로부터 다른 관찰자를 생성할 수 없다.
   - 하나의 관찰자를 다른 관찰자로 재대입할 수 없다.

4. handle 타입은 복사 초기화와 대입을 허용한다.
   - handle의 복사본은 동일한 entity를 가리킨다.
   - handle은 entity의 소유권을 의미하지 않는다.


## 2.4 형변환 규칙

본 언어의 형변환 규칙은 이하의 규칙을 따른다.
1. 암묵적 형변환은 안전한 형변환에서만 가능하다.(안전한 형변환인 이하의 세부 규칙을 따른다)
  1. 암묵적 형변환은 기본 타입에 대해서만 제공된다.
  2. 값 손실이 발생하지 않는 정수 간 형변환
  3. 정밀도를 초과하지 않는 부동소수점 간 형변환
  4. 정확히 표현 가능한 범위 내에서 정수->부동소수점 간 형변환
2. signed와 unsigned간 형변한은 경고를 발생시킨다.
3. 안전한 형변환이 아닌 경우이더라도 명시적 형변환은 사용가능하다.

# 3. 기본 타입
<!--
primitive/builtin 타입 규칙을 정리.
리터럴과 연산 규칙까지 연결되므로 생각보다 중요함.
-->

기본 타입은 타입 생성자이며, 약어는 해당 타입의 구체적인 표현 방식을 지정한다.
약어를 생략할 경우 해당 타입의 기본 타입으로 판단한다.
```txt
<기본 타입>[:<약어>]
int x;        // int:i32로 해석
float y;      // float:f32로 해석
char c;       // char:c8로 해석
string s;     // string:s8로 해석
```


## 3.1 정수 타입
<!--
목록:
- int8/int16/int32/int64 또는 int 등
- 부호 여부
- 기본 정수 리터럴의 추론 규칙
-->

정수 타입의 약어 목록은 다음과 같다.

| 약어 | 설명 | 특징 |
|------|------|------|
| i8   | 8비트 signed형 | |
| i16  | 16비트 signed형 | |
| i32  | 32비트 signed형 | |
| i64  | 64비트 signed형 | |
| i128 | 128비트 signed형 | |
| u8   | 8비트 unsigned형 | |
| u16  | 16비트 unsigned형 | |
| u32  | 32비트 unsigned형 | |
| u64  | 64비트 unsigned형 | |
| u128 | 128비트 unsigned형 | |

정수 리터럴의 기본 타입은 int:i32이다.
리터럴 값이 int:i32의 표현 범위를 초과하는 경우, 해당 값을 표현할 수 있는 가장 작은 signed 정수 타입으로 확장된다.
모든 정수 타입으로도 표현할 수 없는 경우 컴파일 오류로 처리한다.

## 3.2 실수 타입
<!--
float32/float64 또는 float/double 구조
실수 리터럴 기본형도 적기
-->

실수 타입의 약어 목록은 다음과 같다.
| 약어 | 설명 | 특징 |
|------|------|------|
| f16 | 16비트 부동 소수점 | |
| f32 | 32비트 부동 소수점 | |
| f64 | 64비트 부동 소수점 | |
| f128 | 128비트 부동 소수점 | |


실수 리터럴의 기본 타입은 float:f32이다.
리터럴 값이 float:f32의 표현 범위를 초과하는 경우, 해당 값을 표현할 수 있는 가장 작은 실수 타입으로 확장된다.
모든 실수 타입으로도 표현할 수 없는 경우 컴파일 오류로 처리한다.

## 3.3 bool 타입
<!--
bool 리터럴 true/false
허용 연산: &&, ||, !, ==, != 등
금지 연산도 적기
-->
bool 타입은 약어를 가지지 않는다.
bool 리터럴은 true와 false 두 개만 존재한다.

허용 연산:
- 논리 연산: &&, ||, !
- 비교 연산: ==, !=

금지 연산:
- 산술 연산 (+, -, *, / 등)
- 제곱 연산
- 비트 연산

## 3.4 char 타입
char 타입은 이하의 세부 종류를 가진다.
| 약어 | 설명 | 특징 |
|------|------|------|
| c8 | 8비트 UTF-8 코드 유닛 | |
| c16 | 16비트 UTF-16 코드 유닛 | |
| c32 | 32비트 Unicode code point | |

char 리터럴의 기본 타입은 char:c8이다.
리터럴이 c8로 표현될 수 없는 경우, 해당 문자를 표현할 수 있는 가장 작은 char 타입으로 확장된다.

## 3.5 string 타입
string 타입은 이하의 세부 종류를 가진다.


| 약어 | 설명 | 특징 |
|------|------|------|
| s8   | char:c8 문자로 구성된 문자열  | |
| s16  | char:c16 문자로 구성된 문자열 | |
| s32  | char:c32 문자로 구성된 문자열 | |

string 리터럴의 기본 타입은 string:s8이다.
문자열 내 문자를 모두 표현할 수 없는 경우, 해당 문자열을 표현할 수 있는 가장 작은 string 타입으로 확장된다.

## 3.6 기본 타입 리터럴 규칙
<!--
리터럴을 resolver에서 어떻게 해석하는지 기준이 되는 곳.
예:
- 123 -> 기본 int
- 1.0 -> 기본 float
- 'a' -> char
- "abc" -> string
- true/false -> bool
오버플로우/범위 초과시 오류인지도 적기
-->
리터럴은 다음 규칙으로 타입이 결정된다.

- 123 → 정수 리터럴 (기본 int:i32)
- 1.0 → 실수 리터럴 (기본 float:f32)
- 'a' → char 리터럴 (기본 char:c8)
- "abc" → string 리터럴 (기본 string:s8)
- true / false → bool 리터럴

각 리터럴은 기본 타입으로 우선 해석되며, 표현할 수 없는 경우 더 큰 타입으로 확장된다.
모든 후보 타입으로도 표현할 수 없는 경우 컴파일 오류로 처리한다.
리터럴은 명시적 형변환을 통해서만 크기를 명시적으로 할당할 수 있다.

# 4. 객체 모델
<!--
이 언어의 핵심 섹션 중 하나.
class / struct / world / spawn / view가 여기 들어감.
-->

본 언어에서 객체는 value 타입인 struct와 entity 타입인 class로 나뉜다.
value 타입 객체는 직접 선언 및 사용 가능한 객체이다.
entity 타입 객체는 world.spawn을 통해 handle을 생성하고 관찰자를 통해 사용할 수 있다.


## 4.1 struct
<!--
value 타입으로서의 규칙을 적기.
예:
- 일반 값처럼 선언 가능
- 직접 초기화 가능
- 복사/대입 가능
- world.spawn 대상인지 여부
-->
struct는 handle-view 모델을 사용하지 않는 value 타입 객체이다.
struct는 이하의 특징을 가진다.
- 값으로 선언 및 사용가능하다.
- 복사 및 대입 가능하다.
- 직접 초기화 및 사용 가능하다.
- world.spawn 불가능한 객체이다.

### 4.1.1 선언 규칙
struct는 다음의 구조로 선언된다.

```
[접근 제어자] struct <name> {
  //fields
  ...
  [public init(args[]){...}]
}
```

### 4.1.2 생성 규칙

struct는 handle-view 방식으로 생성 관리하지 않는 객체이다.
struct는 직접 생성 가능한 객체이다.

### 4.1.3 초기화 규칙

struct의 초기화는 T() 또는 T(args)를 사용한다.

### 4.1.4 대입/복사 규칙

struct는 대입 가능하며 대입시 값을 복사한다.

## 4.2 class
<!--
entity 타입 규칙.
여기서는 반드시 "직접 생성 불가" 같은 핵심 제한을 명확히 적기.
-->
class는 entity 타입 객체이다.
class는 이하의 특징을 가진다.
- 객체를 직접 생성할 수 없다.
- world.spawn을 통해 handle을 생성할 수 있다.
entity는 관찰자를 통해 접근하며,
관찰자는 객체 복사본이 아니다.

### 4.2.1 선언 규칙

class는 다음 구조로 선언된다.

```
[접근 제어자] class <name> [extends T] [: trait ...]{
  //field
    
[public init(args[]){...}]
}
```

### 4.2.2 생성 규칙
<!--
예:
- class는 직접 생성 불가
- 반드시 world.spawn T(...) 사용
-->


class는 직접 생성이 불가능하며 world.spawn을 통해 간접적으로 생성된다.
class는 관찰자를 통해 사용할 수 있다.

예
```

Handle<T> h = world.spawn T(...);

T v = world.view(h);


```


### 4.2.3 수명 및 소유 개념

모든 entity는 storage에 의해 생성 및 관리된다.

entity는 다음 규칙에 따라 수명을 가진다:

1. entity는 `world.spawn`을 통해 생성된다.
2. entity는 명시적 제거 연산(`world.destroy`)에 의해 제거된다.
3. handle의 소멸은 entity의 소멸을 의미하지 않는다.
4. entity가 제거되면 해당 entity를 가리키는 모든 handle은 invalid 상태가 된다.
5. invalid handle에 대해 접근을 시도하는 것은 오류이다.

본 언어에서 entity의 수명은 handle이 아닌 storage에 의해 관리된다.
## 4.3 Handle<T>

### 4.3.1 정의

handle은 entity 객체를 식별하고 접근하기 위한 값이다.
handle은 entity의 소유권을 나타내지 않으며, 단순한 접근 토큰이다.
Handle<T>는 value 타입으로 취급된다.

### 4.3.2 생성 방법

handle은 `world.spawn`의 결과로 생성된다.

### 4.3.3 허용 연산

handle은 다음을 허용한다:
- 복사
- 대입
- 함수 인자 전달
- 반환 값 사용
- field 및 컨테이너 저장

handle의 복사본은 동일한 entity를 가리킨다.

### 4.3.4 금지 연산

handle을 통한 직접 멤버 접근은 허용되지 않는다.
entity 접근은 반드시 `world.view(handle)`을 통해 수행해야 한다.

### 4.3.5 수명 및 유효성

handle의 소멸은 entity의 소멸을 의미하지 않는다.

entity는 명시적 제거 연산(`world.destroy`)에 의해 제거된다.

entity가 제거된 이후에도 해당 entity를 가리키는 handle은 존재할 수 있으며,
이러한 handle은 invalid handle 상태로 간주된다.

invalid handle에 대해 모든 대입, 복사, 전달하는 것은 오류이다.
## 4.4 관찰자(T)
<!--
너는 view 결과를 별도 문법 타입(View<T>)가 아니라 그냥 T로 통일하기로 했으니,
이 부분을 아주 명확히 적어야 함.
즉, 문법상 T지만 의미상 "관찰자"라는 점을 적어야 함.
-->
관찰자는 문법상 value와 같은 형태를 가지지만, entity 객체를 직접 가리키는 문법이 아닌 생성된 객체에 대한 임시 접근 수단이다.
관찰자는 다음 제약을 가진다:

- 관찰자는 entity가 살아 있는 동안에만 유효하다.
- 관찰자가 생성된 이후 entity가 제거되면 해당 관찰자는 더 이상 유효하지 않다.

### 4.4.1 정의
<!--
예:
- world.view(h)의 결과인 T는 객체 복사본이 아니라 관찰자이다.
- 이 값은 entity 본체를 관찰/접근하기 위한 임시적 접근 수단이다.
-->
world.view(h)의 결과인 T는 객체 복사본이 아니라 관찰자이다.
이 값은 entity 본체를 관찰/접근하기 위한 임시적 접근 수단이다.

### 4.4.2 생성 방법
<!--
예: world.view(handle) -->

world.view(handle);에 의한 반환 값으로 생성된다.

### 4.4.3 연산
<!--
필드 접근, 메서드 호출 등 -->
관찰자는 다음 연산을 허용한다:
- 필드 접근
- 메서드 호출

관찰자는 다음 제약을 가진다:
- 메서드 내부에서의 로컬 변수로써만 선언 및 저장할 수 있다.
- 메서드 외부에서는 선언 및 저장이 허용되지 않는다.
- 재할당이 허용되지 않는다.
- null 값을 가질 수 없다.

### 4.4.4 관찰자와 일반 value 타입 T의 차이
<!--
문법이 같으면 더더욱 반드시 써야 하는 부분.
"표면상 T여도 class 기반 T는 관찰자 의미다" 같은 식으로 적기
-->

class 기반의 타입 T는 문법적으로 value 타입과 동일한 형태를 가지지만,
실제 의미는 entity 객체에 대한 관찰자를 나타낸다.
value 타입에서의 T는 객체 자체를 가리키며 필드에서 선언 가능하다.

# 5. 생성과 초기화
<!--
init 정책은 따로 빼는 게 좋다.
나중에 IR/HIR 만들 때도 생성 규칙이 독립되어 있어야 덜 헷갈림.
-->

## 5.1 value 타입 초기화
<!--
예:
- T x;
- T x = T(...);
- 기본 초기화 허용 여부
- 미초기화 허용 여부
-->

value 타입은 다음 초기화 규칙을 따른다.

- 자동 기본값 초기화는 제공되지 않는다.
- 선언 시 초기화를 생략할 수 있으며, 이 경우 값은 미초기화 상태가 된다.
- 명시적 초기화는 `T()` 또는 `T(args)` 형태로 수행된다.
- 미초기화 상태의 struct 변수에 대해서는 field 접근을 허용하지 않는다.
- `T()` 또는 `T(args)`를 통해 초기화된 struct 변수는 객체 자체가 초기화된 상태로 취급하며, 이후 field별 초기화 상태에 따라 field의 읽기 및 대입 가능 여부를 판단한다.
## 5.2 entity 생성
<!--
예:
- Handle<T> h = world.spawn T(...);
- spawn 대상 타입 제한
-->

entity 타입은 world.spawn을 통해서만 생성 가능하며, 생성 결과로 handle이 반환된다.
entity 객체는 직접 생성할 수 없다.

## 5.3 init
<!--
init의 정체를 명확히 적기.
method인지 별도 특수 멤버인지도 적기.
-->

### 5.3.1 정의
<!--
예:
- init는 객체 초기화용 특수 메서드이다.
- public 강제 여부
- 반환 타입 규칙 (예: void 취급)
-->
init은 객체 초기화용 특수 메서드이다.
init은 public 접근 제어자를 강제한다.
init은 반환 타입을 가지지 않으며, 반환 값을 명시할 수 없다.
init은 일반 메서드와 유사하지만 직접 호출할 수 없는 특수 메서드이다.

### 5.3.2 호출 규칙
<!--
예:
- world.spawn T(args)는 내부적으로 T의 init와 연결된다
- 일반 메서드처럼 직접 호출 가능한지 여부
-->

entity 타입의 경우, `world.spawn T(args)` 호출 시
해당 타입의 init 메서드가 호출되어 객체 초기화가 수행된다.
init 메서드는 직접 호출이 불가능하다.

### 5.3.3 오버로딩 규칙
<!--
허용/금지 명확히 -->

init메서드는 오버로딩이 가능하며 일반 메서드의 오버로딩 규칙을 따른다.
```
class Player {
    public init() {}
    public init(string name) {}
}

```
### 5.3.4 기본 init 규칙
<!--
init가 없을 때 T() 가능한지
init가 하나라도 있으면 기본 생성 금지인지
이런 정책을 명시 -->

init이 없는 경우 T(args) 형태의 생성은 사용할 수 없다.

하나 이상의 init이 정의된 경우, `T()` 호출은 허용되지 않으며,
반드시 정의된 init 중 하나와 일치하는 인자를 사용해야 한다.

### 5.3.5 오류 규칙
<!--
예:
- 일치하는 init 없음
- 접근 불가 init
- entity가 아닌 타입에 spawn 사용
-->

일치하는 init이 없을 경우 오류가 발생한다.
init은 entity 타입과 value 타입 모두에서 정의할 수 있다.

- value 타입의 경우, `T(args)` 형태의 명시적 초기화 시 init이 호출된다.
- entity 타입의 경우, `world.spawn T(args)` 호출 시 init이 호출된다.

### 5.3.6 init과 field의 관계

1. 모든 변수와 field는 미초기화 상태를 가질 수 있다.

2. 미초기화 상태의 변수 또는 field를 읽거나 값으로 사용하는 것은 컴파일 오류이다.

3. init 선언은 필수가 아니다.

4. 객체 생성 시 field 선언에 명시된 초기화식이 먼저 수행된다.

   * field 선언 초기화에 의해 값이 할당된 field는 초기화된 상태로 취급한다.
   * field 선언 초기화가 없는 field는 미초기화 상태로 시작한다.

5. init이 없는 struct는 `T()`만 사용할 수 있으며, 생성 이후 field 초기화 상태는 field 선언 초기화 결과를 따른다.

6. init이 없는 class는 `world.spawn T()`만 사용할 수 있으며, 생성 이후 field 초기화 상태는 field 선언 초기화 결과를 따른다.

7. init이 존재하는 경우, 각 init의 field 초기화 분석은 field 선언 초기화가 수행된 이후의 상태에서 시작한다.

8. init 내부에서 field에 직접 값을 대입하면 해당 field는 이후 경로에서 초기화된 상태로 취급한다.

9. 분기가 존재하는 경우, 해당 init이 종료되는 모든 실행 경로에서 초기화되는 field만 그 init이 보장하는 초기화 field로 취급한다.

10. 메서드 호출에 의해 간접적으로 발생하는 field 대입은 init의 초기화 효과로 인정하지 않는다.

    * init 내부에서 호출한 메서드가 field에 값을 대입하더라도 해당 field의 초기화 여부 계산에는 반영하지 않는다.
    * field의 초기화는 현재 init의 제어 흐름 내에서 직접 확인 가능한 대입만을 기준으로 판단한다.

11. 각 init은 서로 다른 field 초기화 상태를 보장할 수 있다.

12. 특정 init을 통해 생성된 값의 초기화 상태는 실제 호출된 init이 종료된 시점의 field 초기화 상태를 따른다.

13. 일반 메서드 분석 시에는 모든 생성 가능한 init에서 공통으로 초기화가 보장되는 field만 초기화된 상태로 취급한다.

14. init이 존재하지 않는 타입의 일반 메서드 분석 시에는 field 선언 초기화에 의해 초기화된 field만 초기화된 상태로 취급한다.

15. 일반 메서드에서 발생한 field 초기화 효과는 다른 일반 메서드의 초기화 상태로 전파하지 않는다.

16. 일반 메서드는 객체의 초기화 상태를 완성하기 위한 수단으로 취급하지 않는다.
    * 일반 메서드에서 사용하는 field는 해당 메서드의 진입 시점에 이미 초기화가 보장되어 있거나, 해당 메서드 내부에서 사용 전에 직접 초기화되어야 한다.

# 6. 선언과 바인딩
<!--
변수 선언, 상수 선언, mutable 여부 등.
semantic analyzer에서 꽤 많이 얽히는 규칙이라 분리하는 게 좋음.
-->

## 6.1 변수 선언
<!--
예:
- var / let / const 체계
- 타입 명시 필요 여부
- 타입 추론 허용 여부
-->

모든 변수 선언은 다음의 구조를 가진다.
```
[접근 제어자] [const] <타입> <이름> [= <초기화식>];
```
타입 추론은 허용되지 않는다.
접근 제어자는 field 변수에서만 사용할 수 있다.

## 6.2 상수성 / 변경 가능성
<!--
isMutable 같은 내부 규칙의 외부 명세 버전
-->

일반적으로 선언되는 모든 변수는 수정 가능한 상태이다.
상수로 선언하기 위해서는 const 키워드를 사용한다.

## 6.3 초기화 필수 여부
<!--
선언만 가능? 반드시 초기화 필요?
타입별로 다르면 나눠서 써야 함
-->
초기화되지 않은 변수에 대한 읽기 및 사용은 컴파일 오류이다.

value 변수는 초기화 없이 선언 가능하다.
value 변수는 선언 시 미초기화 상태가 될 수 있다.

handle 변수는 초기화 없이 선언 가능하다.
handle 변수는 handle 변수는 world.spawn의 결과 또는 다른 handle의 복사를 통해 값을 가질 수 있다.

관찰자 변수는 선언 시에 world.view(handle)를 통해 초기화되어야만 한다.
관찰자 변수는 메서드 내부에서만 선언될 수 있다.
관찰자 변수는 재할당이 불가능하다.

const는 선언 시에 초가화되어만 한다.


## 6.4 스코프 규칙
<!--
이름이 어디서 보이는지
블록/함수/타입 스코프 등
-->

변수는 해당 스코프 및 스코프 내부에 존재하는 다른 스코프에서 접근 가능하다.
타입 이름과 동일한 이름의 변수가 존재하더라도 타입 위치에서는 항상 타입으로 해석된다.

식 위치에서 이름이 단독으로 사용될 경우 변수로 해석된다.
식 위치에서는 표현식이 올 수 있다.

표현식은 다음을 포함한다:
- 변수 이름
- 함수 호출
- 리터럴
- world.spawn 및 world.view와 같은 내장 표현식
- 연산 표현식 (이항, 단항 등)

식 위치에서 이름이 사용될 경우, 함수 호출 형태 `name(...)`는 함수로 해석되며,
그 외의 경우 변수로 해석된다.

동일 스코프 내에서 동일한 이름의 함수 오버로딩은 허용된다.

## 6.5 중복 선언 규칙
<!--
동일 스코프 내 금지
오버로딩 예외
타입명/변수명 충돌 규칙 등
-->

내부 스코프에서는 외부 스코프와 동일한 이름의 변수를 선언할 수 있다.
이 경우 내부 변수는 외부 변수를 가린다(shadowing).
동일 스코프 내에서 동일한 이름을 가지는 변수는 선언할 수 없다.

타입명과 변수명은 중복될 수 있다.
단, 타입 위치에서는 항상 타입으로 해석된다.

함수명과 변수명은 중복될 수 있다.
단, 함수 호출 형태에서는 함수가 우선적으로 해석된다.

단항 연산자의 해석은 암묵적 형변환 이전의 피연산자 타입을 기준으로 결정된다.

## 7.5 할당 식
할당식은 대입 연산자 및 복합 대입 연산자를 이용한 연산을 의미한다.

| 종류　　　　　　　　　　| 연산자　| 역할　　　　　　　　　　　　　　　　　　　　　　　　　　　　|
| -------------------------| ---------| -------------------------------------------------------------|
| 대입 연산자　　　　　　 | =　　　 | 좌변에 우변을 대입함　　　　　　　　　　　　　　　　　　　　|
| 덧셈 복합 대입 연산자　 | +=　　　| 좌변에 우변을 더한 값을 대입함　　　　　　　　　　　　　　　|
| 뺄셈 복합 대입 연산자　 | -=　　　| 좌변에서 우변을 뺀 값을 대입함　　　　　　　　　　　　　　　|
| 곱셈 복합 대입 연산자　 | *=　　　| 좌변에 우변을 곱한 값을 대입함　　　　　　　　　　　　　　　|
| 나눗셈 복합 대입 연산자 | /=　　　| 좌변을 우변으로 나눈 값을 대입함　　　　　　　　　　　　　　|
| 나머지 복합 대입 연산자 | %=　　　| 좌변을 우변으로 나눴을 때 나머지를 대입함　　　　　　　　　 |
| 제곱 복합 대입 연산자　 | **=　　 | 좌변을 우변만큼 제곱한 값을 대입함.　　　　　　　　　　　　 |
| 비트 and 대입 연산자　　| &=　　　| 좌변과 우변을 비트 and 연산 후 결과를 좌변에 대입함　　　　 |
| 비트 or 대입 연산자　　 | &#124;= | 좌변과 우변을 비트 or 연산 후 결과를 좌변에 대입함　　　　　|
| 비트 xor 대입 연산자　　| ^=　　　| 좌변과 우변을 비트 xor 연산 후 결과를 좌변에 대입함　　　　 |
| 비트 left-shift 연산자　| <<=　　 | 좌변과 우변을 비트 left-shift 연산 후 결과를 좌변에 대입함　|
| 비트 right-shift 연산자 | >>=　　 | 좌변과 우변을 비트 right-shift 연산 후 결과를 좌변에 대입함 |

좌변은 변수, field, 배열 원소와 같은 대입 가능한 표현식이어야 한며, 다음 조건을 만족해야 한다:
- const 변수일 수 없다
- 관찰자는 좌변이 될 수 없다

handle 변수는 미초기화 상태에서만 대입을 통한 초기화가 허용된다.
한 번 초기화된 handle 변수는 다시 대입할 수 없다.
복합 대입 연산은 대응하는 이항 연산을 수행한 뒤 결과를 좌변에 대입한 것과 동일하게 처리한다.

할당식이 연속된 경우 오른쪽에서 왼쪽으로 결합한다.

예:
a = b = c;

위 식은 다음과 같이 처리된다.
b = c;
a = b;

## 7.6 호출 식

호출식은 메서드를 호출하는 연산을 의미한다.
모든 호출식은 다음의 구조를 따른다.
```
<name>(args)
<object>.<name>(args)
```
반환 값을 가지는 호출식은 대입, 단항, 이항, 삼항 연산에서 사용할 수 있다.
반환 값이 없는 호출식은 표현식 문장으로만 사용할 수 있다.

호출식은 함수의 이름과 인자 타입에 따라 오버로딩이 결정된다.
일치하는 오버로드가 없거나 호출이 모호한 경우 컴파일 오류가 발생한다.

init 메서드는 호출식으로 직접 호출할 수 없다.


## 7.7 멤버 접근 식

멤버 접근 식은 해당 객체가 가지는 멤버에 접근하는 연산을 의미한다.
멤버 접근 식을 통해 접근할 수 있는 멤버는 field 변수이다.
멤버 접근 식은 다음의 구조를 따른다.
```
<object>.<member>
```

멤버 접근은 관찰자 및 struct 객체에서만 가능하다.
handle을 통한 직접 멤버 접근은 허용되지 않는다.

## 7.8 배열 접근 식

배열 접근 식은 배열로 선언된 변수에 특정 값에 접근하는 연산이다.
배열 접근 식은 다음의 구조를 따른다.
```
<expr>[<index>]
```
index는 정수 타입의 변수 혹은 리터럴만 위치할 수 있다.

컴파일 시 확인 가능한 범위 초과는 컴파일 오류이다.

## 7.9 삼항 식

삼항 식은 삼항 연산자 이용하는 연산을 의미한다.
삼항 연산자의 구조는 다음을 따른다.

```
<condition>?<then>:<else>
```

조건이 참이면 then을, 아니라면 else를 반환한다.

condition의 결과 타입은 bool이어야 한다.

then과 else는 동일한 타입이거나,
공통 타입으로 변환 가능해야 한다.
삼항 식의 결과 타입은 then과 else의 공통 타입이다.

## 7.10 this/super/self 식

this 및 super는 class 내부의 메서드에서만 사용할 수 있다.
this는 현재 객체의 멤버(field 및 메서드)에 접근할 때 사용한다.
super는 부모 객체의 멤버(field 및 메서드)에 접근할 때 사용한다.
부모가 없는 객체에서 super를 사용 시 컴파일 오류이다.

self는 impl 내부 메서드에서만 사용할 수 있다.
self는 impl 대상 타입의 멤버(field 및 메서드)에 접근할 때 사용한다.

class 내부에서는 this를 생략할 수 있다.
impl 내부에서는 self를 생략할 수 있다.

## 7.11 spawn 식
spawn 식은 entity 객체를 생성하는 식이다.
spawn 식은 handle을 반환한다.

spawn 식은 다음의 구조를 가진다.

```
world.spawn T(args)
```
T는 class(entity 타입)이어야 한다.

spawn은 새로운 entity를 생성하며 spawn 식의 결과 타입은 Handle<T>이다.
spawn 식은 생성된 객체에 대해 일치하는 init을 호출한다.
일치하는 init이 없으면 컴파일 오류이다.

## 7.12 view 식
<!--
실제 AST 노드 구조에 맞춰 적는 것이 좋음.
이러면 구현과 문서가 대응됨.
-->

view 식은 handle을 통해 entity 객체에 대한 관찰자를 생성하는 표현식이다.
view 식의 결과 타입은 handle이 가리키는 entity 타입 T이다.
단, 해당 값은 value 객체가 아닌 관찰자로 취급된다.
view의 인자는 Handle<T> 타입이어야 한다.

view 식은 다음의 구조를 가진다.
```
world.view(handle)
```

view는 다음 규칙을 따른다:

1. handle은 유효한 entity를 가리켜야 한다.
2. invalid handle에 대해 view를 호출하는 것은 오류이다.
3. view는 entity에 대한 임시 관찰자를 반환한다.

## 7.13 match 식
<!-- match가 중요하면 expression과 statement를 구분해서 적기 -->

match는 다음의 규칙을 따른다.

1. match는 값을 계산하기 위한 분기 표현식이다.
2. match는 다음 형식을 따른다.
  
  ```
    match (표현식) {
      case 값 => { << expr; }
  }
  ```
3. match의 기준 표현식은 정확히 한 번만 평가된다.
4. case의 선택 값(selector)은 리터럴 상수 또는 enum variant 항목만 허용한다.
5. case는 위에서 아래 순서로 평가되며, 기준 값과 동일한 첫 번째 case가 선택된다.
6. case의 본문은 {}로 묶인 문 블록(statement block)이어야 한다.
7. case 블록 내부에서는 값 전달 연산 << expr;만 반환 수단으로 허용한다.
8. << expr;가 실행되면 match 표현식은 즉시 종료되고 해당 값이 결과로 반환된다.
9. 모든 << expr의 타입은 동일하거나 공통 타입으로 변환 가능해야 한다.
10. case에 다중 선택 값은 허용하지 않는다.
11. case _는 와일드카드 선택자로서 허용되며, 반드시 마지막 위치에만 선언할 수 있다.
12. case _는 다른 case가 하나 이상 존재하는 경우에만 사용할 수 있다.
13. default 선택자는 허용하지 않는다.
14. break 및 continue 문은 match 내부에서 사용할 수 없다.
15. 동일한 선택 값을 가지는 case를 중복 선언할 수 없다.
16. match가 모든 경우를 처리하지 못하는 경우 컴파일 오류이다.

# 8. 문장(Statement)
<!-- 표현식과 별개로 문장을 정리. return, if, while, for, block 등 현재 구현 범위까지만 적어도 됨. -->
## 8.1 블록

블록은 중괄호 `{}`로 구성되는 문장의 집합이며, 독립적인 스코프를 생성한다.
블록 내부에서 선언된 변수는 해당 블록과 그 하위 블록에서만 접근할 수 있다.
내부 블록에서는 외부 블록과 동일한 이름의 변수를 선언할 수 있다.
이 경우 내부 변수는 외부 변수를 가린다(shadowing).

## 8.2 표현식 문장

표현식 문장은 평가 가능한 표현식 뒤에 세미콜론(`;`)을 붙여 구성된다.
표현식 문장은 모든 표현식을 허용한다.

값을 반환하는 표현식의 결과가 사용되지 않는 경우,
컴파일러는 경고를 발생시킬 수 있다.

## 8.3 변수 선언 문장

변수 선언 문장은 변수 선언 구문으로 구성되며, 세미콜론(`;`)으로 종료된다.

## 8.4 if 문


1. `if` 문 형식은 다음과 같다.

```
if (조건) body

if (조건) body
else body

```

2. `body`는 단일 문 또는 block 문이다.
3. 조건식은 표현식이어야 한다.
4. 조건식의 결과 타입은 `bool`이어야 한다.
5. else 절은 선택 사항이다.
6. else는 가장 가까운 if와 결합된다.
  ```
  if (a)
      if (b)
          foo();
      else
          bar();
  
  ```
위 코드는 다음과 동일하게 해석된다.
  ```
  if (a) {
      if (b)
          foo();
      else
          bar();
  }
  ```
7. else if는 별도의 문법이 아니며, else 블록 내부의 if 문과 동일하게 처리된다.
  ```
  if (a)
      foo();
  else if (b)
      bar();  
  ```
  는 다음과 동일하다.
  ```
  if (a)
    foo();
  else {
      if (b)
          bar();
  }
  ```

## 8.5 while 문

1. `while` 문 형식은 다음과 같다.

```
while (조건) body

```

2. `body` 규칙은 `if` 문과 동일하다.
3. 조건식은 `bool` 타입이어야 한다.
4. 조건식은 각 반복 시작 시마다 다시 평가된다.
5. break와 continue는 while 문 내부에서 사용할 수 있다.

## 8.6 for 문

for 문은 범위 기반 for문과 반복자 기반 for 문으로 나뉜다.


### 8.6.1 범위 기반 for 문

1. 범위 기반 for 문의 형태는 다음과 같다.
```
for (<변수 선언>; <시작값>..<끝값> [by <증감값>]) body
```

2. 변수 선언은 초기화를 금지한다.
3. 반복 방향과 증감 방향이 일치하지 않을 경우 컴파일러는 경고를 발생시킬 수 있다.
4. 증감값은 정수 타입은 1을 기본값으로 가지며, 그 외의 타입은 명시적으로 작성해야 한다.
5. `body` 규칙은 if 문과 동일하다.
6. 반복 변수는 for 문의 body 내부에서만 유효하다.
7. 증감값은 0일 수 없다.
8. 시작값, 끝값, 증감값 표현식은 반복 시작 전에 한 번만 평가된다.

* int 이외의 범위 값은 구현 예정

### 8.6.2 반복자 기반 for 문
미정

## 8.7 return 문
1. `return` 문은 다음 두 형태를 허용한다.
    - `return;`
    - `return expr;`
2. `return expr;`은 `func` 함수의 반환 타입 추론 근거가 된다.
3. 하나의 함수 내 여러 `return expr;`이 존재할 경우, 모든 `expr`의 타입은 동일해야 한다.
4. `return;`은 func 함수의 반환 타입을 void로 추론할 수 있다.
5. 명시적 반환 타입 함수는 (`void` 제외) 반드시 모든 경로에서 `return expr;`을 포함해야 한다.
6. `void` 반환 함수 및 `func` 함수는 `return` 생략을 허용한다.
7. func 함수와 반환값이 있는 함수 모두 return; 과 return expr;를 혼용하여 사용할 수 없다.
8. init메서드 내부에서는 return 문을 사용할 수 없다.

## 8.8 break / continue
`break`는 `for`, `while` 문에서만 사용 가능하다.
`break`는 `match`, `switch` 문에서는 사용할 수 없다.
break문은 가장 가까운 반복문을 즉시 종료시킨다.

`continue`는 `for`, `while` 문에서만 사용 가능하다.
현재 반복을 종료하고 다음 반복으로 진행한다.
`continue`는 `match`, `switch` 문에서는 사용할 수 없다.

break와 continue는 가장 가까운 반복문에만 적용된다.

## 8.9 switch 문
<!-- match가 중요하면 expression과 statement를 구분해서 적기 -->
1. switch는 제어 흐름을 위한 분기문이다.
2. switch는 값을 반환하지 않는다.
3. switch는 다음 형식을 따른다.
   ```
    switch (expression) {
        case <value>=>{...}
        default=>{...}
    }
    
   ```
4. switch의 기준 표현식은 정확히 한 번만 평가된다.
5. case 선택 값(selector)은 리터럴 상수 또는 열거형(enum) 항목만 허용한다.
6. case는 위에서 아래 순서로 평가되며, 일치하는 case의 블록이 실행된다.
7. case는 여러 개의 선택 값을 가질 수 있다.
  ```
  switch(e){
      case a,b,c=>{
        ...
      }
  }
  ```
8. case의 본문은 {}로 묶인 문 블록(statement block)이어야 한다.
9. switch는 암묵적 fallthrough를 허용하지 않는다.
10. default 선택자는 마지막에 한 번만 선언할 수 있다.
11. case _ 선택자는 switch에서 사용할 수 없다.
12. break 및 continue 문은 switch 내부에서 사용할 수 없다.
13. 동일한 선택 값을 가지는 case를 중복 선언할 수 없다.
14. 각 case 블록은 실행 후 자동으로 종료된다.
15. switch의 기준 표현식이 enum 타입인 경우, 모든 variant를 처리하거나 default 선택자를 포함해야 한다.

## 8.10 onexit 문

* 구현 예정

`onexit`는 **스코프 종료 시 자동으로 실행되는 제어문(statement)**이다.

블록 스코프의 수명에 종속되며, 해당 스코프를 어떤 방식으로 벗어나든(정상 종료, return, break, continue, throw) 반드시 실행된다.

이 문법은 자원 정리, 상태 복구, 후처리 로직을 명시적으로 표현하기 위한 수단이다.
onexit는 다음의 구조를 가진다.

```
onexit <statement>;
onexit {
    statements...
}

```


- `onexit`는 **블록 스코프 내부에서만 선언 가능**하다.
- 선언된 `onexit`는 **자신이 선언된 블록 스코프가 종료될 때 실행**된다.
- 함수 종료, 반복문 탈출, 예외 전파 등 **종료 원인은 구분하지 않는다**.

- 동일한 스코프 내에 여러 개의 `onexit`가 존재할 수 있다.
- 실행 순서는 **LIFO (Last In, First Out)** 이다.
- 즉, **가장 나중에 선언된 onexit가 가장 먼저 실행**된다.

```
{
    onexit A();
    onexit B();
}
// 실행 순서: B → A

```

`onexit` 내부에서는 **모든 제어 흐름 변경을 금지**한다.

금지되는 항목:

- `return`
- `break`
- `continue`
- `throw`

이는 `onexit`가 **정리 단계(cleanup phase)** 로서만 동작하도록 강제하기 위한 설계다.

`onexit`는 흐름을 바꾸지 않으며, 오직 “종료 시 실행”이라는 의미만을 가진다.

## 8.10 destroy 문

destroy 문은 entity 객체를 명시적으로 제거하는 문이다.
destroy는 idempotent하지 않다.
즉 동일한 entity에 대해 두 번 이상 호출하는 것은 오류이다.

destroy 문은 다음의 구조를 가진다.

```
world.destroy(handle)
```
destroy는 다음 규칙을 따른다:

1. handle은 제거할 entity를 가리켜야 한다.
2. destroy는 해당 entity를 제거한다.
3. 제거된 entity를 가리키는 모든 handle은 invalid 상태가 된다.
4. 이미 제거된 entity에 대해 destroy를 호출하는 것은 오류이다.
5. destroy는 값을 반환하지 않는다.

invalid handle에 대해 허용되는 연산은 다음과 같다:

- 복사: 허용
- 미초기화 handle 변수에 대한 초기화 대입: 허용
- 이미 초기화된 handle 변수에 대한 재대입: 오류
- destroy: 오류
- view: 오류

invalid handle은 null과 같은 특별 값이 아니며,
단순히 더 이상 유효한 entity를 가리키지 않는 상태이다.
entity가 제거되면 해당 entity에 대한 모든 관찰자는 더 이상 유효하지 않다.

destroy는 값을 반환하지 않으며, 표현식 위치에서 사용할 수 없다.

## 8.11 quit 문

quit 문은 프로그램 종료를 요청하는 문이다.
quit 문이 동작한 프레임 내의 연산이 모두 완료되면 프로그램을 종료시킨다.
이미 종료 요청 상태라면 추가 호출은 무시된다.

* async 내부에서의 동작은 미정이다.


quit 문은 다음의 구조를 지닌다.
```
world.quit();
```

## 9. 함수와 메서드
<!-- 함수/메서드의 차이, 멤버 스코프, 오버로딩 정책을 정리 -->
메서드 선언은 다음의 구조를 가진다.
```
[접근 제어자] <타입> <이름>([args]){
...
}
```
타입에는 value 객체의 타입과 enum타입, 그리고 추론 타입인 func이 위치할 수 있다.
observer는 반환타입이 될 수 없으며 handle<T>는 가능하다.

### 9.1 전역 함수
전역 함수는 존재하지 않는다.
모든 함수는 타입(class/struct)에 소속된 메서드이다.
### 9.2 메서드
본 언어에서 함수는 존재하지 않으며 명시되는 모든 함수는 메서드이다.

### 9.3 매개변수 규칙
<!-- 네가 "_" 표기를 중요하게 보고 있었으니 여기에 확실히 적기 -->

매개변수 선언은 변수 선언 규칙을 따르며 ',' 로 각각의 매개변수를 구분한다.
함수 호출 시에는 표현식을 매개변수로 넣을 수 있으며'_' 사용시 매개변수의 기본 값을 사용한다.
'_'는 기본값이 설정된 매게변수에서만 사용할 수 있다.
'_'는 위치 기반으로만 해석되며, 이름 기반 매칭은 지원하지 않는다.

### 9.4 반환 규칙
함수의 반환은 선언시 정의되는 타입을 따른다.
모든 반환값은 함수의 반환 타입에 대해 암묵적 형변환이 가능한 타입이여야 한다.
`func`으로 선언된 함수는 내부 return 의 반환 값을 통해 반환 타입이 결정되며 return이 없거나 return;형태라면 void로 취급한다.

### 9.5 오버로딩 규칙
가장 정확히 일치하는 오버로드가 선택된다.
모호한 경우 컴파일 오류가 발생한다.
오버로딩된 함수 호출시 매게변수의 타입과 갯수로 함수를 찾으며 같은 갯수의 인자를 가지는 함수가 있을 경우 '_'를 사용할 수 없다.

### 9.6 접근 제한자
접근 제어자는 public/protected/private이 있다.
public은 모든 위치에서 접근 가능하다.
protected는 상속관계에서 super혹은 암묵적 super에 의한 멤버 접근으로만 접근 가능하다.
private는 해당 객체 내부에서만 접근 가능하다.

### 9.7 override / async / frame 등 수식자
<!-- 각 modifier의 허용 위치와 의미를 적기 -->

override는 extends로 상속한 객체의 함수를 재작성할때 사용하는 수식자이다.
override를 생략하고 상속한 객체의 함수를 재작성 할 수 없다.

frame은 메인 함수에서 반복 연산되는 함수에서 사용하는 수식자이다.
frame함수 내에서 async 함수 호출을 금지한다.

async는 비동기 처리 함수를 선언할 때 사용하는 수식자이다.
* 세부 사항은 미정이다.

## 10 case/default 세부 규칙
<!-- CaseValueExpr 규칙을 여기서 명세화 -->

### 10.1 case 값 규칙
case value는 리터럴과 enum variant만 위치할 수 있다.
switch에서 case value는 복수의 값을 가질 수 있다.
단 payload는 예외적으로 단독 값만 허용한다.
match에서 case value는 단일 값만 허용한다.

### 10.2 default 규칙
default 및 와일드카드 _ 는 case중 마지막 위치에만 위치할 수 있다.
default 및 와일드카드 _는 case에서 처리하지 못한 값을 처리할때 사용한다.
default는 switch문에서만 사용가능하며 match문에서는 금지한다.
와일드 카드 _는 match문에서만 사용가능하며 switch문에서는 금지한다.

### 10.3 exhaustiveness 검사  
<!-- 필수인지, verifier에서 검사하는지 -->

exhaustiveness 검사는 swtich와 match에서 모든 가능성을 포함하는지를 확인하는 검사이다.
match는 verifier 단계에서 모든 가능성을 포함하는지 확인하며 모든 가능성을 포함하지 않으면 오류를 발생시킨다.
switch는 verifier 단계에서 variant의 모든 가능성을 포함하는지 확인하며 모든 가능성을 포함하지 않으면 오류를 발생시킨다.

---
## 11. enum

`enum`은 **유한한 값 집합**을 표현하는 타입이다.

- 각 항목은 **payload를 가질 수 있다**
- payload는 **자료형 정보 중심**으로 구성된다

enum은 다음의 구조를 가진다.

```
[access_modifier] enum <Identifier>{
<enum_cases>
}

```

- `enum`은 상속을 제공하지 않는다.

- `enum` payload에 value 객체의 타입만 허용한다.
enum 값은 일반 표현식에서 사용 가능한 값 타입이다.

### 11.1 enum variant

enum variant는 enum에서 정의된 상수 값을 의미한다.
enum variant는 다음의 구조를 가진다.
```
<name>[(type)]

```

같은 enum 내부에서 이름 중복은 불가능하다.
payload는 하나의 타입만 허용한다.

variant 생성은 다음의 구조를 따른다.
```
<EnumName>.<VariantName>
<EnumName>.<VariantName>(<expression>)
```

## 12. impl

`impl`은 다음 역할을 수행한다.

- `struct`에 대한 **구현부 정의**
- 인스턴스 메서드의 **실제 동작 정의**
- 타입의 멤버 필드에 대한 **암묵적 접근 문맥(self) 제공**

impl은 다음의 구조로 선언된다.

```
impl <TypeIdentifier> {
<method_declarations>
}

impl <TypeIdentifier> : <trait1>, <trait2> ...{
<method_declarations>
}

```

- `impl`은 타입 정의(`struct`)와 **분리된 구현 블록**이다.
- 하나의 타입에 대해 **여러 개의 impl 블록을 허용**한다.
- `impl` 블록은 **새로운 타입을 정의하지 않는다.**
- impl을 통해 trait계약 구현 시 일반 메서드 선언을 금지한다.
- impl을 통해 trait계약 구현 시 같은 trait 여러번 구현할 수 없다.


`impl`의 대상이 될 수 있는 것은 다음과 같다.

- `struct`

다음은 `impl`의 대상이 될 수 없다.

- `trait`
- `class`
- `enum`

`impl` 블록 내부에서 선언된 함는 **해당 타입의 메서드**로 간주된다.

```
impl Vec2 {
    func sum() {
        return x + y;
    }
}

```

- `impl` 내부의 `func`는 전역 함수가 아니다.
- 메서드는 **암묵적인 self 문맥**을 가진다.

### 12.1 self 문맥

- `self`는 impl 메서드 내부에서만 존재하는 **암묵적 객체 참조**이다.
- `self`의 타입은 impl 대상 타입이다.
- `self`는 문법적으로 명시되지 않아도 항상 존재한다.

개념적으로 다음은 동등하다.

```
x
```

```
self.x
```

impl 메서드 내부에서 식별자는 다음 순서로 해석된다.

1. 지역 변수
2. 함수 파라미터
3. `self`의 멤버
4. 오류 (undeclared identifier)

즉, 동일한 이름의 지역 변수가 존재할 경우, 멤버보다 **항상 우선한다**.

- `self`는 **메서드 본문(body) 내부에서만 유효**하다.
- 중첩된 블록(`if`, `while` 등)에서도 유지된다.
- impl 외부에는 `self`가 존재하지 않는다.

- impl 자체는 이름 해석 스코프가 아니다.
- 메서드 내부의 스코프는 **일반 함수와 동일한 lexical scope 규칙**을 따른다.
- `self`는 스코프가 아니라 **해석 규칙**이다.
- struct의 멤버는 메서드의 스코프 트리에 병합되지 않는다.
- class는 선언과 동시에 메서드를 정의하며, impl을 사용하지 않는다.
---

## 13. trait

`trait`는 **인터페이스 전용 타입**이다.

- 메서드 **시그니처만 정의**
- 구현을 포함하지 않는다
- trait은 다른 trait을 상속할 수 없다.

trait 구현은 다음과 같이 정의한다:
```
impl <TypeName> : <traitName> ... {
    <method_implementations>
}
```

- `trait` 내부에는:
    - 메서드 시그니처만 허용
    - 필드, 구현, 실행문은 허용되지 않는다.

trait은 타입 제약으로 사용할 수 있다.
trait 타입을 통한 동적 디스패치는 지원하지 않는다.

trait을 impl을 통해 구현할 때의 일반 메서드 선언은 금지된다.
동일한 trait을 여러 번 impl할 수 없다.

trait 계약 구현시 class는 선언에서 명시한다.
trait 계약 구현시 struct는 impl을 통해 간접적으로 명시되며, struct는 직접적으로 trait의 계약을 구현 및 명시하지 않는다.
```
class Player : Drawable {
}

struct Vec2 {
}

impl Vec2 : Drawable {
}

```

trait을 구현하는 타입은 trait에 선언된 모든 메서드를 구현해야 한다.
구현되지 않은 메서드가 존재할 경우 컴파일 오류이다.

---

## 14. 모듈과 import

본 언어에서 파일은 하나의 독립적인 모듈 단위이자 이름 공간을 구성한다.

`import`는 다른 파일의 내용을 현재 파일에 삽입하는 기능이 아니다.
`import`는 대상 파일이 공개한 타입 선언을 현재 파일의 이름 탐색 범위에 추가하는 선언이다.

모듈과 import는 다음 목적을 가진다.

1. 파일 간 타입 선언 참조
2. 프로젝트 내부 코드의 논리적 분리
3. 외부 모듈 의존성 참조
4. 동일한 타입 이름 간 충돌 방지
5. 파일 단위 컴파일 및 링크 의존성 구성

---

## 14.1 용어

### 14.1.1 프로젝트 모듈

프로젝트 모듈은 하나의 컴파일 및 배포 단위를 의미한다.

하나의 프로젝트는 하나의 루트 모듈을 가진다.

외부 라이브러리와 표준 라이브러리 또한 각각 독립된 모듈로 취급한다.

예:

```txt
game
physics
hwarangdo
```

### 14.1.2 파일 모듈

하나의 소스 파일은 하나의 파일 모듈을 구성한다.

파일 모듈의 경로는 해당 파일이 속한 프로젝트 모듈의 소스 루트를 기준으로 결정된다.

예:

```txt
src/math/vector.hgm
```

위 파일의 프로젝트 내부 경로는 다음과 같다.

```txt
math.vector
```

프로젝트 모듈 이름이 `game`인 경우 전체 경로는 다음과 같다.

```txt
game::math.vector
```

### 14.1.3 모듈 경로

모듈 경로는 다음 요소로 구성된다.

```txt
[프로젝트 모듈::]디렉터리.파일
```

프로젝트 모듈 이름과 파일 내부 경로는 `::`로 구분한다.

파일 내부의 디렉터리와 파일 이름은 `.`으로 구분한다.

예:

```txt
math.vector
game::math.vector
physics::collision.shape
```

---

## 14.2 import 선언 문법

`import` 선언은 다음 형식을 가진다.

```txt
import <파일 경로>;
import <파일 경로>.{<타입 목록>};
```

외부 프로젝트 모듈을 참조하는 경우 다음 형식을 사용한다.

```txt
import <모듈 이름>::<파일 경로>;
import <모듈 이름>::<파일 경로>.{<타입 목록>};
```

문법은 다음과 같다.

```ebnf
ImportDecl
    := "import" ImportTarget ";"

ImportTarget
    := [ModuleName "::"] FilePath [SelectiveImport]

FilePath
    := Identifier ("." Identifier)*

SelectiveImport
    := "." "{" TypeNameList "}"

TypeNameList
    := Identifier ("," Identifier)*

ModuleName
    := Identifier
```

예:

```hwarangdo
import math.vector;
import math.matrix.{Matrix3, Matrix4};

import physics::collision.shape;
import physics::collision.collider.{Collider};
```

---

## 14.3 import 선언 위치

`import`는 파일 최상위에서만 선언할 수 있다.

모든 import 선언은 해당 파일의 타입 선언보다 먼저 위치해야 한다.

허용:

```hwarangdo
import math.vector;
import physics::collision.shape.{Circle};

public struct Position {
}
```

금지:

```hwarangdo
public struct Position {
}

import math.vector;
```

다음 위치에서는 import를 선언할 수 없다.

* class 내부
* struct 내부
* enum 내부
* trait 내부
* impl 내부
* 메서드 내부
* 블록 내부

---

## 14.4 현재 프로젝트 모듈 참조

모듈 이름이 생략된 import는 현재 프로젝트 모듈을 기준으로 해석한다.

프로젝트 모듈 이름이 `game`인 경우 다음 두 경로는 동일한 파일 모듈을 가리킨다.

```hwarangdo
import math.vector;
```

개념적으로는 다음과 같다.

```hwarangdo
import game::math.vector;
```

현재 프로젝트 내부의 파일을 import할 때는 프로젝트 모듈 이름을 생략한다.

현재 프로젝트 모듈 이름을 명시적으로 작성하는 것은 허용하지 않는다.

금지:

```hwarangdo
import game::math.vector;
```

현재 프로젝트 내부 경로는 다음과 같이 작성해야 한다.

```hwarangdo
import math.vector;
```

이는 프로젝트 이름 변경이 프로젝트 내부의 모든 import 선언에 영향을 주는 것을 방지한다.

---

## 14.5 외부 프로젝트 모듈 참조

외부 프로젝트 모듈을 import할 때는 프로젝트 모듈 이름을 반드시 명시한다.

외부 프로젝트 모듈 이름과 내부 파일 경로는 `::`로 구분한다.

```hwarangdo
import physics::collision.shape;
```

위 선언은 다음 파일 모듈을 참조한다.

```txt
프로젝트 모듈: physics
파일 경로: collision/shape.hgm
```

외부 프로젝트 모듈은 현재 프로젝트의 의존성 목록에 등록되어 있어야 한다.

의존성으로 등록되지 않은 프로젝트 모듈을 import하는 것은 컴파일 오류이다.

```hwarangdo
import unknown::utility.math;
```

`unknown`이 현재 프로젝트의 의존성으로 등록되어 있지 않다면 오류가 발생한다.

---

## 14.6 파일 단위 import

파일 단위 import는 대상 파일 모듈이 공개한 모든 최상위 타입을 현재 파일의 이름 탐색 범위에 추가한다.

```hwarangdo
import math.vector;
```

대상 파일:

```hwarangdo
// math/vector.hgm

public struct Vec2 {
}

public struct Vec3 {
}

private struct VectorStorage {
}
```

import 이후 현재 파일에서 사용할 수 있는 타입:

```txt
Vec2
Vec3
```

사용할 수 없는 타입:

```txt
VectorStorage
```

파일 단위 import는 대상 파일의 `public` 최상위 타입만 가져온다.

---

## 14.7 선택적 타입 import

선택적 타입 import는 대상 파일 모듈이 공개한 타입 중 명시된 타입만 현재 파일의 이름 탐색 범위에 추가한다.

```hwarangdo
import math.vector.{Vec2};
```

여러 타입을 동시에 선택할 수 있다.

```hwarangdo
import math.vector.{Vec2, Vec3};
```

선택적 import에 명시되는 이름은 대상 파일의 최상위 타입 이름이어야 한다.

다음 선언은 허용되지 않는다.

* 대상 파일에 존재하지 않는 타입
* `private` 최상위 타입
* 타입 내부의 멤버
* 메서드
* 필드
* enum variant

예:

```hwarangdo
import math.vector.{length};
```

`length`가 메서드인 경우 컴파일 오류이다.

---

## 14.8 import 가능한 선언

import 대상이 될 수 있는 선언은 다음과 같다.

* class
* struct
* enum
* trait

import 대상이 될 수 없는 선언은 다음과 같다.

* 메서드
* init
* 필드
* 지역 변수
* enum variant
* impl 블록
* 실행 문장

`impl`은 독립된 타입 선언이 아니므로 직접 import할 수 없다.

대상 struct가 import되면 해당 struct에 연결된 impl 구현은 컴파일 및 링크 과정에서 함께 연결된다.

---

## 14.9 접근 제한자

다른 파일 모듈에서 import할 수 있는 선언은 `public` 최상위 타입으로 제한한다.

`private` 최상위 타입은 선언된 파일 내부에서만 접근할 수 있다.

`protected`는 상속 관계의 멤버 접근을 위한 접근 제한자이므로 최상위 타입 선언에는 사용할 수 없다.

허용:

```hwarangdo
public struct Vec2 {
}

private struct VecStorage {
}
```

금지:

```hwarangdo
protected struct Vec2 {
}
```

import 여부는 타입 내부 멤버의 접근 제한을 변경하지 않는다.

예를 들어 public class를 import하더라도 해당 class의 private 멤버에는 접근할 수 없다.

---

## 14.10 이름 탐색

import된 타입은 현재 파일에서 단순 타입 이름으로 참조한다.

```hwarangdo
import math.vector.{Vec2};

public struct Position {
    Vec2 value;
}
```

import 경로는 표현식이나 타입 이름의 일부로 직접 사용할 수 없다.

금지:

```hwarangdo
math.vector.Vec2 value;
```

금지:

```hwarangdo
physics::collision.shape.Circle value;
```

모듈 경로는 import 선언에서만 사용한다.

일반 코드에서는 import된 타입의 이름을 사용한다.

---

## 14.11 이름 충돌

서로 다른 파일 모듈에서 동일한 이름의 타입을 import할 수 없다.

예:

```hwarangdo
import game.player.{State};
import network.connection.{State};
```

두 import가 모두 `State`를 현재 파일에 추가하므로 컴파일 오류가 발생한다.

파일 단위 import에서도 동일한 규칙을 적용한다.

```hwarangdo
import game.player;
import network.connection;
```

두 파일이 모두 `public State`를 선언한다면 이름 충돌 오류가 발생한다.

이름 충돌은 실제 타입 사용 여부와 관계없이 import 선언을 처리하는 시점에 진단한다.

현재 버전에서는 다음 기능을 제공하지 않는다.

* import alias
* 타입 alias
* qualified type name을 이용한 충돌 해소

이름 충돌은 import 대상을 줄이거나 타입 이름을 변경하여 해결해야 한다.

예:

```hwarangdo
import game.player.{Player, PlayerState};
import network.connection.{Connection};
```

---

## 14.12 중복 import

같은 파일 모듈을 여러 번 import하는 것은 허용한다.

```hwarangdo
import math.vector;
import math.vector;
```

동일한 import는 한 번만 적용된다.

선택적 import가 중복되는 경우에도 한 번만 적용된다.

```hwarangdo
import math.vector.{Vec2};
import math.vector.{Vec2};
```

파일 단위 import와 선택적 import가 함께 선언되는 경우 파일 단위 import가 전체 공개 타입을 이미 포함하므로 선택적 import는 추가 효과를 가지지 않는다.

```hwarangdo
import math.vector;
import math.vector.{Vec2};
```

이 경우 오류는 발생하지 않는다.

컴파일러는 중복 import에 대해 경고를 발생시킬 수 있다.

---

## 14.13 import의 비전이성

import는 다른 파일로 전파되지 않는다.

파일 A:

```hwarangdo
import math.vector.{Vec2};

public struct Transform {
    Vec2 position;
}
```

파일 B:

```hwarangdo
import game.transform;

public struct ObjectData {
    Vec2 position;
}
```

파일 B는 파일 A가 import한 `Vec2`를 직접 사용할 수 없다.

파일 B에서 `Vec2`를 사용하려면 직접 import해야 한다.

```hwarangdo
import game.transform;
import math.vector.{Vec2};
```

즉 import는 재수출되지 않으며, 각 파일은 자신이 직접 사용하는 외부 타입을 직접 import해야 한다.

단, 공개 타입의 멤버 시그니처에 포함된 타입 정보는 해당 타입의 구조를 해석하기 위해 컴파일러 내부에서 참조할 수 있다.

이 동작은 해당 타입 이름을 현재 파일의 이름 탐색 범위에 추가하지 않는다.

---

## 14.14 순환 import

파일 모듈 간 순환 import는 허용한다.

파일 A:

```hwarangdo
import game.b.{B};

public class A {
    Handle<B> target;
}
```

파일 B:

```hwarangdo
import game.a.{A};

public class B {
    Handle<A> target;
}
```

순환 import는 파일 로드 순서에 영향을 주지 않는다.

컴파일러는 전체 import 그래프의 파일을 먼저 수집한 뒤, 최상위 타입 선언을 등록하고 타입 간 연결을 수행한다.

순환 import 자체는 오류가 아니다.

다음 경우에는 순환 관계와 별개로 오류가 발생할 수 있다.

* 잘못된 상속 순환
* 무한한 value 타입 포함 관계
* trait 계약 순환에 의한 불변식 위반
* 존재하지 않는 타입 참조

---

## 14.15 파일 경로 해석

파일 경로의 각 `.` 구분 요소는 디렉터리 또는 파일 이름을 나타낸다.

마지막 요소는 파일 이름으로 해석한다.

```hwarangdo
import math.geometry.vector;
```

위 경로는 다음 파일을 참조한다.

```txt
math/geometry/vector.hgm
```

선택적 타입 import에서도 `{}` 앞까지가 파일 경로이다.

```hwarangdo
import math.geometry.vector.{Vec2};
```

파일 경로:

```txt
math/geometry/vector.hgm
```

타입 이름:

```txt
Vec2
```

따라서 파일 이름과 타입 이름의 경계는 `{}` 문법으로 명확하게 구분된다.

컴파일러는 파일 시스템을 탐색하여 마지막 식별자가 파일인지 타입인지 추측하지 않는다.

---

## 14.16 소스 루트

프로젝트 모듈은 하나 이상의 소스 루트를 가질 수 있다.

import 경로는 소스 루트를 제외한 상대 경로로 작성한다.

예:

```txt
project/
├── src/
│   └── math/
│       └── vector.hgm
└── project 설정 파일
```

`src`가 소스 루트인 경우 다음과 같이 import한다.

```hwarangdo
import math.vector;
```

다음과 같이 실제 파일 시스템 경로를 직접 작성할 수 없다.

```hwarangdo
import src.math.vector;
```

금지되는 경로 표현:

```txt
./math/vector.hgm
../common/vector.hgm
/math/vector.hgm
C:\project\math\vector.hgm
```

import는 논리적 모듈 경로만 허용한다.

상대 경로 import는 지원하지 않는다.

---

## 14.17 파일 이름 규칙

import 경로에 사용되는 디렉터리 및 파일 이름은 식별자 규칙을 따라야 한다.

허용:

```txt
math.vector
game_object.player_state
```

허용되지 않는 예:

```txt
math.2d_vector
game-object.player
```

소스 파일 확장자 `.hgm`은 import 선언에 작성하지 않는다.

허용:

```hwarangdo
import math.vector;
```

금지:

```hwarangdo
import math.vector.hgm;
```

---

## 14.18 대소문자 구분

모듈 이름, 디렉터리 이름, 파일 이름 및 타입 이름은 대소문자를 구분한다.

다음은 서로 다른 경로로 취급한다.

```txt
math.vector
Math.vector
math.Vector
```

import 경로의 대소문자는 실제 모듈 및 파일 경로와 정확히 일치해야 한다.

대소문자를 구분하지 않는 파일 시스템에서도 컴파일러는 논리적 모듈 경로의 대소문자를 엄격하게 검사한다.

---

## 14.19 파일 로드와 컴파일

컴파일러는 루트 파일에서 시작하여 import된 파일을 재귀적으로 수집한다.

파일 수집은 다음 순서를 따른다.

1. 루트 파일 로드
2. import 선언 분석
3. 프로젝트 모듈 및 외부 의존 모듈 확인
4. 대상 파일 경로 해석
5. 아직 로드되지 않은 파일 로드
6. 전체 import 그래프 완성
7. 최상위 타입 심볼 등록
8. 타입 간 연결
9. 본문 분석
10. HIR 및 이후 단계 진행

동일한 파일 모듈은 전체 컴파일 과정에서 한 번만 파싱하고 분석한다.

import 선언의 순서는 타입 해석 결과에 영향을 주지 않는다.

---

## 14.20 진입점과 import

일반 파일 모듈은 `Main` class를 포함하지 않아도 된다.

실행 파일 생성 시에는 전체 컴파일 대상 모듈에서 유효한 `Main` class를 탐색한다.

진입점 규칙은 다음과 같다.

1. import된 일반 파일에는 `Main`이 없어도 된다.
2. 전체 프로그램에는 정확히 하나의 유효한 `Main` class가 존재해야 한다.
3. 둘 이상의 유효한 `Main` class가 존재하면 컴파일 오류이다.
4. 실행 파일 생성 시 `Main` class가 존재하지 않으면 컴파일 오류이다.
5. 독립적인 라이브러리 모듈 컴파일에서는 `Main` class를 요구하지 않는다.

`Main` class는 현재 프로젝트 모듈에 선언되어야 한다.

외부 의존 모듈에 선언된 `Main`은 현재 프로그램의 진입점 후보로 취급하지 않는다.

---

## 14.21 외부 모듈 의존성

외부 모듈은 프로젝트 설정에 명시된 의존성만 import할 수 있다.

예:

```hwarangdo
import physics::collision.shape;
```

`physics` 모듈이 프로젝트 의존성 목록에 등록되어 있어야 한다.

직접 의존하지 않는 모듈을 간접 의존성을 통해 import할 수 없다.

예:

```txt
game → physics → math
```

`game`이 `physics`에만 의존하고 `math`에 직접 의존하지 않는 경우:

```hwarangdo
import math::vector;
```

는 허용되지 않는다.

`math`를 사용하려면 현재 프로젝트가 `math`를 직접 의존성으로 선언해야 한다.

이는 import 의존성이 다른 모듈을 통해 암묵적으로 전파되는 것을 방지한다.

---

## 14.22 표준 라이브러리

표준 라이브러리는 독립된 프로젝트 모듈로 취급한다.

표준 라이브러리의 모듈 이름은 별도 명세에서 정의한다.

표준 라이브러리 import도 일반 외부 모듈 import와 동일한 문법을 사용한다.

예:

```hwarangdo
import hwarangdo::text.string_builder.{StringBuilder};
```

일부 기본 타입 및 언어 내장 기능은 import 없이 사용할 수 있다.

import 없이 사용할 수 있는 내장 선언의 범위는 표준 라이브러리 명세에서 별도로 정의한다.

---

## 14.23 지원하지 않는 기능

현재 import 문법에서는 다음 기능을 지원하지 않는다.

### wildcard 타입 import

금지:

```hwarangdo
import math.vector.{*};
```

파일 전체를 import하려면 파일 단위 import를 사용한다.

```hwarangdo
import math.vector;
```

### alias import

금지:

```hwarangdo
import math.vector.{Vec2 as Vector2};
```

금지:

```hwarangdo
import physics::collision.shape as Shape;
```

### 상대 경로 import

금지:

```hwarangdo
import ..common.vector;
```

### qualified type name

금지:

```hwarangdo
math.vector.Vec2 value;
```

### import 재수출

금지:

```hwarangdo
public import math.vector;
```

### 런타임 동적 import

금지:

```hwarangdo
import(path);
```

모든 import 대상은 컴파일 시점에 결정되어야 한다.

---

## 14.24 오류 규칙

다음 경우 컴파일 오류가 발생한다.

1. import 선언이 파일 최상위가 아닌 위치에 존재하는 경우
2. 타입 선언 이후에 import가 존재하는 경우
3. 대상 프로젝트 모듈이 존재하지 않는 경우
4. 대상 프로젝트 모듈이 의존성으로 등록되지 않은 경우
5. 대상 파일이 존재하지 않는 경우
6. 선택한 타입이 대상 파일에 존재하지 않는 경우
7. 선택한 타입이 public이 아닌 경우
8. 동일한 이름의 타입이 여러 import를 통해 유입되는 경우
9. import 경로가 식별자 규칙을 위반하는 경우
10. import 경로에 파일 확장자를 작성한 경우
11. 현재 프로젝트 모듈 이름을 `::` 앞에 명시한 경우
12. import 대상이 타입이 아닌 선언인 경우
13. 같은 선택적 import 목록에 동일한 타입 이름을 중복 작성한 경우
14. 선택적 import 목록이 비어 있는 경우
15. import 경로의 대소문자가 실제 경로와 일치하지 않는 경우

## 14.25 사용 예시

프로젝트 구조:

```txt
game/
├── src/
│   ├── Main.hgm
│   ├── math/
│   │   ├── vector.hgm
│   │   └── matrix.hgm
│   ├── entity/
│   │   ├── player.hgm
│   │   └── enemy.hgm
│   └── system/
│       └── movement.hgm
└── 프로젝트 설정 파일
```

`math/vector.hgm`:

```hwarangdo
public struct Vec2 {
    float x;
    float y;
}

public struct Vec3 {
    float x;
    float y;
    float z;
}

private struct VectorStorage {
}
```

`entity/player.hgm`:

```hwarangdo
import math.vector.{Vec2};

public class Player {
    Vec2 position;

    public init(Vec2 position) {
        this.position = position;
    }
}
```

`system/movement.hgm`:

```hwarangdo
import math.vector.{Vec2};
import entity.player.{Player};

public struct Movement {
    public void move(Player player, Vec2 direction) {
        player.position += direction;
    }
}
```

`Main.hgm`:

```hwarangdo
import math.vector.{Vec2};
import entity.player.{Player};
import system.movement.{Movement};

public class Main {
    public init() {
    }

    public frame void update() {
    }
}
```

외부 모듈 사용:

```hwarangdo
import physics::collision.shape.{Circle, Rectangle};
import physics::collision.collider.{Collider};
```

파일 전체 import:

```hwarangdo
import math.vector;
```

선택적 타입 import:

```hwarangdo
import math.vector.{Vec2, Vec3};
```

## 14.26 핵심 규칙 요약

* 하나의 소스 파일은 하나의 파일 모듈을 구성한다.
* import는 텍스트 삽입이 아니라 타입 심볼 가시성 선언이다.
* 현재 프로젝트 내부 import에서는 프로젝트 모듈 이름을 생략한다.
* 외부 모듈은 `module::path.file` 형식으로 참조한다.
* 파일 단위 import는 해당 파일의 모든 public 최상위 타입을 가져온다.
* 선택적 import는 `path.file.{Type}` 형식을 사용한다.
* 모듈 경로와 일반 타입 이름은 분리된다.
* import는 다른 파일로 재수출되지 않는다.
* 직접 사용하는 타입은 각 파일에서 직접 import해야 한다.
* 순환 import는 허용한다.
* import alias와 qualified type name은 현재 지원하지 않는다.
* 파일 모듈에는 Main이 없어도 되며, 실행 프로그램 전체에서만 Main을 검사한다.
